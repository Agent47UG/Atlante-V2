 ATLANTE → "INFINITE" EDITION
 How the live, internet-fed, shared, fast version works — plus what to build
 and set up, in plain language.
═══════════════════════════════════════════════════════════════════════════════

Today: all data lives in one file (graph.ts) loaded into the browser.
Goal:  data is pulled from the internet, shared between all users, grows
       forever, and still loads fast.


───────────────────────────────────────────────────────────────────────────────
 1. THE BIG PICTURE (diagram)
───────────────────────────────────────────────────────────────────────────────

                          ┌─────────────────────────┐
                          │        THE USER          │
                          │   (browser / your app)   │
                          └────────────┬─────────────┘
                                       │ clicks a node
                                       ▼
        ┌──────────────────────────────────────────────────────────┐
        │  LAYER 1 — BROWSER MEMORY / IndexedDB                     │
        │  "Have I seen this node already?"                         │
        │  YES → show instantly (0 ms, works offline)              │
        └───────────────┬──────────────────────────────────────────┘
                        │ NO (not seen)
                        ▼
        ┌──────────────────────────────────────────────────────────┐
        │  LAYER 2 — CDN (your pre-made "core" files)              │
        │  Small ready-made JSON files, copied to servers near     │
        │  the user. Your week of exploring lives here.            │
        │  HIT → ~20 ms (feels instant)                            │
        └───────────────┬──────────────────────────────────────────┘
                        │ MISS (not part of core)
                        ▼
        ┌──────────────────────────────────────────────────────────┐
        │  LAYER 3 — YOUR SERVER (a small API function)            │
        │  Checks a fast cache, then the database.                 │
        │   • cache hit  → ~5 ms                                   │
        │   • database   → ~30 ms                                  │
        └───────────────┬──────────────────────────────────────────┘
                        │ MISS (brand-new, nobody's ever visited)
                        ▼
        ┌──────────────────────────────────────────────────────────┐
        │  LAYER 4 — WIKIDATA + WIKIPEDIA (the internet)           │
        │  Fetch the node + neighbors. ~300–800 ms, ONCE.         │
        │  Then SAVE it to the database so it's fast forever,     │
        │  for everyone.                                           │
        └──────────────────────────────────────────────────────────┘

   RESULT:
     • Explored / core areas  → instant
     • Brand-new territory    → one short pause, then saved for all
     • Return visits          → instant (browser remembers)

   Data flows UP as well as down: every new node discovered at Layer 4 is
   written back into the database (Layer 3) and, later, baked into the
   core files (Layer 2). The map grows itself.


───────────────────────────────────────────────────────────────────────────────
 2. WHAT EACH PIECE IS (in plain words)
───────────────────────────────────────────────────────────────────────────────

 • Node        = one concept (Zero, Newton, Rome). Identified by its Wikidata
                 "Q-number" (Newton = Q935). This is its unique ID everywhere.

 • Wikidata    = a free public database of facts. Gives structure: what a thing
                 is, what it connects to, its location (lat/lon), its date.

 • Wikipedia   = free public summaries + thumbnail images for each thing.

 • Database    = ONE shared place on a server that stores every node/edge your
                 app has ever discovered. The single source of truth.

 • Server API  = a tiny program that sits between the app and the database +
                 internet. The app never talks to the database directly.

 • CDN         = a service that copies your static files to servers worldwide so
                 they load fast near each user.

 • IndexedDB   = a storage box inside the user's browser that remembers data
                 between visits.


───────────────────────────────────────────────────────────────────────────────
 3. THE SHARED DATABASE — SHAPE (simple)
───────────────────────────────────────────────────────────────────────────────

 Two tables. Keep it boring and simple.

 nodes
 ─────
   id          (Q-number, e.g. "Q935")   ← unique key
   label       ("Isaac Newton")
   type        (person / place / concept / technology / ...)
   summary     (paragraph of text)
   lat, lon    (for the globe; may be empty)
   year        (for the timeline; may be empty)
   image_url   (thumbnail link; may be empty)
   pinned      (true = part of your curated core, protected)
   created_at

 edges
 ─────
   source      (Q-number)
   target      (Q-number)
   label       ("influenced", "invented", ...)

 Rule: a node is stored ONCE (keyed by Q-number), so two users reaching the
 same thing never make duplicates.


───────────────────────────────────────────────────────────────────────────────
 4. WHAT ONE CLICK FETCHES (keep it tiny)
───────────────────────────────────────────────────────────────────────────────

 A click loads just ONE node file, e.g. /graph/Q935.json :

   {
     "id": "Q935",
     "label": "Isaac Newton",
     "type": "person",
     "summary": "...",
     "lat": 52.8, "lon": 0.5, "year": 1643,
     "image": "https://.../newton.jpg",
     "neighbors": [
        { "id": "Q7604", "label": "Albert Einstein", "type": "person" },
        { "id": "Q11660", "label": "Calculus",       "type": "concept" },
        ...  (just id + label + type — enough to draw the dots)
     ]
   }

 Neighbors are lightweight "stubs." You only load a neighbor's FULL file when
 the user clicks it. This is why it stays fast — a few KB per click.


───────────────────────────────────────────────────────────────────────────────
 5. STEP-BY-STEP: HOW TO BUILD IT
───────────────────────────────────────────────────────────────────────────────

 PHASE 0 — Prep (no user-facing change yet)
   0.1  Learn the two internet sources by hand first:
          • Wikidata query tool:  https://query.wikidata.org  (test SPARQL)
          • Wikipedia summary API: /api/rest_v1/page/summary/{Title}
   0.2  Write a small "fetch one node + neighbors from Wikidata/Wikipedia"
        function. Test it in isolation until a Q-number returns clean data.
   0.3  Write a "translate Wikidata → your KnowledgeNode shape" mapper
        (map Wikidata types → your person/place/concept/technology types;
         keep only neighbors that have a Wikipedia page, so you skip junk).

 PHASE 1 — Turn the graph into a "store" instead of a fixed file
   1.1  Replace the frozen NODES/EDGES in graph.ts with a mutable store
        (a Map you can add to at runtime).
   1.2  Make neighborsOf()/node lookup ASYNC: "do I have it? if not, fetch it."
   1.3  Add loading states in GraphExplorer (a pulsing dot while a node loads).
        ✓ At this point the app works live off the internet — but with no
          server yet (each browser fetches on its own). Good for YOUR seeding.

 PHASE 2 — Your "seeding week"
   2.1  Just explore. Every node you open gets fetched + saved into your
        browser's IndexedDB (and optionally exported to JSON files).
   2.2  After a week you have a curated core, similar to today's dataset but
        internet-sourced and richer (coords, dates, images).
   2.3  Export that core to per-node JSON files (Q935.json, etc.).

 PHASE 3 — Add the shared server + database (the "collective" step)
   3.1  Create the database (start with SQLite/Turso or Postgres) using the
        two tables above. Import your seeded core; mark those rows pinned=true.
   3.2  Write ONE small server API with 2 jobs:
          GET  /node/:id   → return node+neighbors (cache → DB → Wikidata)
          (writes happen internally when Wikidata is hit)
   3.3  Point the app at this API instead of calling Wikidata directly.
        Now everyone shares the same growing data.

 PHASE 4 — Make it fast
   4.1  Put the pinned CORE as static JSON on a CDN. Most clicks hit these.
   4.2  Add a fast cache (Redis or in-memory) in front of the DB.
   4.3  Save browser copies in IndexedDB so return visits are instant.
   4.4  Prefetch: when a node loads, quietly load its neighbors in the
        background so the NEXT click feels instant.
   4.5  Make new-node writes happen in the background (user never waits).

 PHASE 5 — Stories from the internet
   5.1  Keep your current text→path story builder, but run it over the live
        graph (fetch-and-walk from both ends until the paths meet).
   5.2  Optional "magic" version: send the real path (node summaries + edge
        verbs) to an LLM to write the captions. The GRAPH keeps it factual;
        the LLM only writes the prose between real stops.
        (The LLM key lives on the SERVER, never in the app.)

 PHASE 6 — Keep it healthy
   6.1  Notability filter: skip entities with no Wikipedia page.
   6.2  Protect the pinned core from being overwritten.
   6.3  Optionally review/prune low-quality frontier nodes later.

 6. WHAT YOU NEED TO SET UP (checklist)
───────────────────────────────────────────────────────────────────────────────

 Already have:
   [x] The app (React + Vite + Three.js)
   [x] The data model (KnowledgeNode / edges / civilizations)

 Need to add:

 CODE
   [ ] lib/wikidata.ts   — fetch + translate Wikidata/Wikipedia → your node
   [ ] a graph "store"   — mutable, async, cached (replaces static graph.ts)
   [ ] loading states    — in GraphExplorer + globe markers for any node

 SERVER (new — this is the main new thing you don't have yet)
   [ ] A place to run a small API. Easiest: serverless functions on
       Vercel / Netlify / Cloudflare Workers (free tiers exist).
   [ ] The API endpoint:  GET /node/:id   (cache → DB → Wikidata → save)

 DATABASE (pick ONE to start)
   [ ] SQLite via Turso (simple, cheap, fast, edge-friendly)   ← good first pick
       or Postgres via Supabase/Neon (managed, more powerful)
   [ ] The two tables: nodes, edges

 SPEED LAYERS
   [ ] CDN hosting for the static core JSON (Vercel/Netlify/Cloudflare do this)
   [ ] A cache in front of the DB (Redis via Upstash, or just in-memory)
   [ ] IndexedDB in the browser (a small library like "idb" helps)

 OPTIONAL (for LLM-narrated stories)
   [ ] An LLM API key (kept on the server only)

 ACCOUNTS you'd likely create (all have free tiers):
   [ ] Vercel OR Netlify OR Cloudflare   (host app + API + CDN)
   [ ] Turso OR Supabase OR Neon         (database)
   [ ] Upstash                            (Redis cache) — optional
   [ ] An LLM provider                    — optional


───────────────────────────────────────────────────────────────────────────────
 7. SUGGESTED ORDER (smallest risk first)
───────────────────────────────────────────────────────────────────────────────

   1) Phase 0 + 1  → app runs live from the internet (no server). Feels similar
                     to today, but data is fetched. Lowest risk, big learning.
   2) Phase 2      → spend your week seeding a good core.
   3) Phase 3      → add DB + API so it becomes shared/collective.
   4) Phase 4      → add CDN + caching + prefetch for speed.
   5) Phase 5      → upgrade stories (graph paths, then optional LLM).

   You can STOP after any phase and still have something that works.
   Phases 0–2 alone already give you a "living" Atlante for yourself.


───────────────────────────────────────────────────────────────────────────────
 8. ONE-LINE SUMMARY
───────────────────────────────────────────────────────────────────────────────
 Fetch each node from Wikidata/Wikipedia on click → store it once in a shared
 database → keep fast copies in front (CDN + browser) → load tiny pieces and
 look one step ahead. The map fills itself and never stops growing.
